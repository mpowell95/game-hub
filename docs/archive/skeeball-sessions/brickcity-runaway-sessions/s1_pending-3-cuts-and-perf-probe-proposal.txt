## Proposal — three changes, ranked by what actually bit today

### 1. A runtime perf probe — `test-skeeball-perf.mjs` (highest value by far)

The two things that caused the 10 fps aren't per-machine and aren't in the spec at all. **One test would have caught the whole thing before you ever saw it.** Mount Skeeball in a real browser, play/abandon six racks, and assert:

| assertion | what it catches | today's numbers |
|---|---|---|
| live WebGL contexts ≤ 1 while playing, 0 on the gallery | the leak that throttled the browser | was 12 before the first ball, +1/rack, cap hit at rack 4 |
| exactly 1 `_frame` call per animation frame, after 6 racks | duplicated render loops | was 1 → 2 → 3 → 4 |
| GPU texture count returns to baseline after a rack | popup texture leak | ~1 MB/rack, never freed |
| idle draw calls under a ceiling | shadow map redrawing a still scene | 172 vs 138 |

That's ~30 seconds and it's board-independent — it covers every machine that exists and every one that doesn't yet.

### 2. `PART 7 — THE MACHINE MUST NOT MAKE THE HUB SLUGGISH` in MACHINE-SPEC.md

Rule ids in the existing style, waivable only by you:

- **`perf.context`** — one context per Renderer, exposed as `this.renderer`, released on dispose. **This is currently an undocumented contract**: `ui.js`'s `releaseRenderer` reaches in via `r.renderer.forceContextLoss()`. A machine that renames that field leaks a context per rack and throttles the whole hub, silently. That alone is worth writing down.
- **`perf.probe`** — no per-instance `getContext('webgl')`; memoise per module, release via `WEBGL_lose_context`.
- **`perf.shadow`** — `shadowMap.autoUpdate = false`, `needsUpdate` set only when a caster moved.
- **`perf.textures`** — a texture made per event is disposed with its material (`.map.dispose()` first).
- **`perf.broadphase`** — a world with one dynamic body doesn't use `NaiveBroadphase`.

Most are greppable from the machine's source, so they go straight into `test-skeeball-machine-spec.mjs`, which already runs over every board automatically — a new machine is covered the day its folder appears.

Also add these to section 19's checklist, which currently sends a new machine off with four checks and none of them perf.

### 3. Backfill the other four machines

Three defects × four machines. Mechanical, and each is verifiable the way brickcity's was (the broadphase one needs the 861-throw equivalence proof per machine). **This needs your explicit go-ahead** — the HARD RULE says I don't touch another machine's engine on my own initiative, and you've been burned by exactly that before.
