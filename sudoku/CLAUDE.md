# Sudoku — game documentation

> **THE LAW applies here.** Player data is never deleted, never lost, never put at risk. THE LAW
> and its nine working rules live at the top of the root `CLAUDE.md`, which is always loaded
> alongside this file; the full rules with rationale are in `js/CLAUDE.md`. Nothing below overrides
> them. This game's answer to THE LAW is short and is stated under "Persistence".

Classic 9x9 Sudoku. Four difficulties, notes (pencil marks), undo, hints, a timer and a mistakes
counter. Solo, no opponent. Built 2026-09-12.

## Grading: by TECHNIQUE, not by givens count alone

A puzzle is generated by building a full solved grid first (randomised backtracking, the standard
trick that makes full-grid generation fast — a few milliseconds), then digging cells out one at a
time in random order, checking after every removal that the puzzle still has **exactly one
solution** (`solver.js`'s `countSolutions`, capped at 2). A cell whose removal breaks uniqueness is
put back. This guarantees every shipped puzzle has one solution by construction; `js/test.js`
still verifies it independently over hundreds of generated puzzles.

`gradeGrid()` then applies four human techniques, in order, and reports the hardest one needed:

1. naked single (a cell has exactly one candidate)
2. hidden single (a digit has exactly one legal cell in a row/col/box)
3. pointing pair / box-line reduction (candidate-eliminating, not placing)
4. naked pair / hidden pair (candidate-eliminating, not placing)

| Tier | Grade rule | Givens (as shipped, measured) |
|---|---|---|
| easy | solves with singles only (technique <= 2) | 38-45 |
| medium | needs technique 3 or 4 at least once, does not stall | 23-34 (see below) |
| hard | the technique solver stalls (needs backtracking); givens >= 27 | 27-31 |
| expert | stalls; givens <= 26 | 22-26 |

**Easy, hard and expert are generated the same way**: dig to a random target inside the tier's
givens window, grade the result, and retry (advancing the seed) if the grade does not match —
measured, this converges in 1 attempt for easy, up to about 5-7 for hard/expert, all comfortably
under a phone's frame budget (means: easy ~1-2ms, hard ~3ms, expert ~10ms per puzzle).

**Medium needed a different digging strategy, and this is the one thing in this file worth reading
carefully before touching the generator.** Measured: a puzzle that genuinely needs technique 3 or
4 but does not stall is *rare* under plain random digging at a "medium" givens count — about 1 in
150 attempts. Reaching for more attempts would blow the generation budget; reaching for a wider
givens window does not help, because these techniques rarely matter until digging is pushed
further than an unconstrained dig usually goes. So `digForMedium()` dig cells one at a time,
**accepting a removal only when the puzzle stays solvable by the technique set** (never stalls),
and **stops the instant the puzzle first needs technique 3 or 4** — the least-dug, highest-givens
puzzle that qualifies as medium along that particular random order. If an entire random order digs
all the way down without ever requiring a technique past singles, that order produced an `easy`
puzzle instead and the generator tries a new seed (up to the shared 40-attempt cap; measured,
medium succeeds within 40 attempts essentially always, at a mean of roughly 100-130ms per puzzle —
well inside the 400ms budget, though noticeably slower than the other three tiers, which is the
honest cost of this tier being rare rather than a performance bug).

**The consequence: medium's *shipped* givens range (23-34, measured) overlaps hard's and expert's,
and is wider than the handoff's original planning table (32-37) suggested.** That original range
was a guess made before generation was tried; givens count is explicitly a secondary signal here
(see the table above) — what actually defines a tier is the grade, not a density target. Do not
"fix" this by forcing medium's puzzles into a narrower band; that would mean digging past the
point that first requires technique 3/4, which reintroduces exactly the rarity problem this
digging strategy exists to solve.

**On exhaustion (all 40 attempts fail to produce the requested grade) the generator ships the
closest-graded attempt and logs loudly** (`console.error`) rather than hang — a phone must never
spin forever on this. `js/test.js`'s per-tier assertions tolerate up to 3 such mismatches out of a
20-puzzle sample without failing the suite, which is what "closest grade, logged" is for.

## The `sd` shape, and the zero-sentinel rule

```js
sd: {
  solved: 0,      // lifetime puzzles solved (additive)
  perfect: 0,     // solved with 0 mistakes AND 0 hints (additive)
  hints: 0,       // lifetime hints used (additive)
  mistakes: 0,    // lifetime mistakes (additive)
  bestTimeMs: { easy: 0, medium: 0, hard: 0, expert: 0 },  // LOWER is better; 0 = never set
}
```

`bestTimeMs` is the one lower-is-better best in this repo's aggregation layer, which is otherwise
built entirely on `Math.max` (`docs/BUILDING-A-GAME.md` item 7: *bests take Math.max, never a
sum*). **0 is the "never set" sentinel, exactly Battleship's `fewestShotsWin` precedent** — never
a real elapsed time. `recordSudoku()` (`js/game-stats.js`) only ever writes a nonzero `timeMs`,
and `js/players-agg.js`'s merge branch guards the same way on both sides of the `Math.min`, so a
fresh device with no Sudoku history can never zero another device's best on sync.

`total`/`byDiff` follow every other solo puzzle's convention: a solve is `played+1, won+1` (there
is no loss state), so `byDiff[<tier>].won` is "puzzles solved at this tier" for free — the same
maths Nuts & Bolts and Pipes already use, which is why `js/leaderboard-ui.js`'s
`gameMetricAt()` needs no Sudoku-specific branch (the default `winsAtTier` already answers the
right question).

**There is deliberately no fastest-time record on the leaderboard.** A `TEXTURE` entry's `get`
ranks higher-is-better everywhere else in this file; `bestTimeMs` would need its own inverted
comparator, which is exactly the kind of one-off the shared aggregation layer is built to avoid.
`sd.solved` and `sd.perfect` are the two Standing Records chips instead.

## The save shape (`gamehub.sudoku.save.v1`)

```js
{ v: 1, tier, givens: '81 chars, 0 for blank', solution: '81 chars',
  cells: '81 chars, 0 for blank', notes: [ [digits...] x 81 ],
  elapsedMs, mistakes, hints, undo: [...bounded to 200], startedAt, updatedAt }
```

Written after every input. A malformed or missing save starts a fresh puzzle rather than crashing
(`SudokuGame.fromSave` try/catches and returns `null` on anything unexpected — root `CLAUDE.md`'s
profile-reader rule, same discipline). A finished puzzle clears the save: it is not history, and
the record of a solve is `recordSudoku()` in `gamehub.stats`, never this key.

**Unlike Pipes, a save here is not validated by regenerating the puzzle from a seed** — the save
carries the puzzle and solution VERBATIM rather than a `(tier, seed)` pair, because this
generator's grading loop is not a pure function of `(tier, seed)` alone in the way Pipes' is (the
medium path advances the seed internally while searching for a qualifying order). Storing the
actual puzzle sidesteps that entirely and is simpler to reason about; the tradeoff is that the
save is a little larger (three 81-character strings) and cannot detect "this puzzle came from an
old generator version" the way Pipes' reconstruction check can. That is an acceptable tradeoff
here: unlike Pipes' full-net rule (which changed mid-flight and stranded real boards), this game's
win condition — every cell matches the solution — has never changed and cannot make an old saved
puzzle invalid.

## Colorblind-safe state

Every state below carries a non-color signal; hue is never the only one (root `CLAUDE.md`,
"Accessibility").

| State | Non-color signal |
|---|---|
| given vs player digit | given is bold/heavier (`font-weight: 800`); player digit is regular weight |
| selected cell | a thick (3px) outline |
| same-digit highlight | an underline under the digit, not just a background fill |
| conflict / mistake | a strikethrough on the digit, plus `aria-label="conflict"` |
| notes mode active | the control's icon changes AND its own label switches to "Notes on" |

The selection outline uses `#ffce3a`, the repo's standing selection/emphasis accent, always paired
with the outline shape itself — never color alone.

## Timer

Starts on the **first input** of a completely fresh puzzle (nothing placed, no mistakes, no
hints); a **resumed** in-progress puzzle keeps counting immediately on mount, since the player has
already started it. Pauses on `visibilitychange` (tab hidden) and on unmount (`destroy()`),
resumes when the tab becomes visible again while a puzzle is mounted and unsolved. `elapsedMs` is
the only persisted value; the running extra since the last resume is computed live
(`_currentElapsed()`) and never written to storage mid-tick, so a crash mid-game loses at most the
current tick, never the accumulated total.

## What the tests cover, and what they do not

`node sudoku/js/test.js` (48 assertions): the backtracking solver against 3 known puzzles; the
solution counter's three cases (unique / under-constrained / contradictory); 200 full-grid
generations, all valid; all four tiers' generators (uniqueness, grade match with the
fallback-on-exhaustion tolerance described above, generation time under budget, attempts under the
cap); the technique grader against a known easy puzzle (singles-only) and a known expert puzzle
(stalls); and `game.js`'s placement/conflict/notes/undo/hint/win/save-round-trip behaviour.

**Not covered by any headless test**: the DOM layer (`ui.js`) beyond `test-visual.mjs`'s one PLAY
probe (start a puzzle, tap an empty cell, tap a digit, confirm it landed) and the fit/scroll checks
(`check-no-scroll.mjs`, `test-visual.mjs`'s `fit` probe). Nothing here exercises real multi-device
sync of `sd.bestTimeMs` against a live Firebase project — the zero-sentinel guard is proven by the
`players-agg.js` merge logic and by `players-agg.test.mjs`'s structural probe, not by an
end-to-end sync test.
