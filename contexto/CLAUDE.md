# Contexto — game documentation

> **THE LAW applies here.** Player data is never deleted, never lost, never put at risk. THE LAW
> and its nine working rules live at the top of the root `CLAUDE.md`, which is always loaded
> alongside this file; the full rules with rationale are in `js/CLAUDE.md`. Nothing below overrides
> them. This game's answer to THE LAW is short and is stated under "Persistence".

A clone of contexto.me: one secret word a day, and every guess is answered with its RANK — how
close it is in meaning to the secret, where the secret is rank 1 and the whole ~20-40k-word
vocabulary is ranked below it. Find rank 1 to win. Solo, no opponent. Built 2026-09-28.

## Two languages, and they are NOT the same choice (mirrors Boggle)

Exactly the same split `boggle/CLAUDE.md`'s "Spanish gameplay" documents, and for the same reason:
**the hub's UI language and the puzzle's WORD-LIST language are independent settings.** The hub
language (`js/i18n.js`) sets the chrome (buttons, messages, the how-to sheet); `gamehub.contexto.v1`'s
`lang` sets which of `data/en.*`/`data/es.*` the puzzle is drawn from and which words are legal
guesses. The hub language supplies the DEFAULT the first time only (`getLang()`); once a value is
stored, it always wins, so switching the hub to Spanish never moves a player off the English puzzle
they've been solving, and a Spanish-speaking player can play the English word list on purpose (to
play with someone who doesn't read Spanish) without that being fought by the hub toggle.

Switching the language chip re-fetches the OTHER language's ~3.7 MB data file on first use (cached
in module scope afterward, same `loadModelCached` shape Boggle's `dict.js` uses) and moves to that
language's OWN puzzle #N — a completely different secret word, with its own separate save entry
(see "Persistence" below). **Do not unify the two settings** — see Boggle's file for the fuller
argument against exactly that "simplification".

## The data files are LAZY, not REST or SHELL

Same reasoning as Boggle's word lists (root `CLAUDE.md`'s service-worker section, "A third tier:
LAZY"): `contexto/data/{en,es}.{json,bin}` are large (~3.7 MB per language) and useless to anyone
who never opens this game, so they must not be in the atomic `SHELL` (would block install) or the
eagerly-warmed `REST` tier (would download for every install regardless of interest). They stay in
`ASSETS` (hash-tracked, cache-first, cached on demand) and are marked `LAZY` so `warmRest()` never
fetches them proactively — `js/engine.js`'s `loadModel()` is what actually triggers the fetch, on
first play. **The cost, accepted**: a device that has never opened Contexto cannot play it offline
the first time; `js/ui.js`'s `renderErrorScreen()` (translated `load_error` + `Try again`, plus a
retry on the `online` event) is the honest failure path for that, same shape as Boggle's
`renderLoadError`.

## Persistence

Two keys, additive, THE LAW rule 5 (old shapes never repurposed) applies to any future revision.

- **`gamehub.contexto.v1`** — `{ v:1, lang: 'en'|'es' }`. A preference (rule 2's carve-out): saved
  the moment the language chip changes.
- **`gamehub.contexto.save.v1`** — `{ v:1, games: { "<lang>:<secretWord>": { n, guesses:
  [{w, hint}], done: null|'won'|'gave', recorded } } }`.
  - **Keyed by the SECRET WORD, not the puzzle number.** `build-contexto-data.mjs`'s header states
    the secrets list is append-only, so a puzzle number's meaning never changes in practice — but
    keying by word means even a REGENERATED data file (a re-run of the generator with a different
    vocabulary size or ordering) can never corrupt a save: the entry simply keys under whatever
    word it always was, and a stale entry for a word no longer in a fresh vocabulary just stops
    being reachable rather than silently attaching to a different secret.
  - **Guesses are stored as WORD STRINGS, never indices.** `js/ui.js`'s `_rankedGuesses()`
    re-`lookup()`s each stored word and re-`rankOf()`s it against the current model on every
    render, for the same regenerated-data-safety reason above — an index into a dropped or
    reordered word list would silently point at the wrong word.
  - **`recorded` is the once-only guard** for `recordContexto()` (THE LAW rule 2: a lifetime
    counter must never be incremented twice for one finished puzzle). Set and persisted in the
    same step `done` is set, before the recorder is even called, so a write failure inside the
    recorder itself can't leave the guard unset and the puzzle re-recordable.
  - **Hints are guesses too** (`{w, hint:true}`), so they occupy a rank on the board and are
    excluded from `hintRank()`'s next pick, but they are counted separately (`hints` in
    `recordContexto`'s extras) and never counted toward the typed `guesses` total.

## Hints: `hintRank`, never the word itself

`hintRank(best, taken)` (`js/engine.js`) halves the distance from the best rank reached so far
down toward rank 1 (starting at 300 if nothing is close yet), skips any rank already on the board,
and **structurally cannot return rank 1** — its search floor is 2, so a hint can bring a player
arbitrarily close but a hint alone can never end the puzzle. Only a typed guess that happens to be
the secret wins. `js/test.js` asserts this directly (`'hint is never the word itself'`).

## Ranks beyond the generator's exact neighbour list are approximate

`engine.js`'s header states this plainly and it is worth repeating here because it directly shapes
what "closest words" (the result panel's pager, ranks 1-100) and the guess-list bars can promise:
ranks 2 through K+1 (K=1000 in the shipped data) are the GENERATOR's exact top-K neighbours,
computed at full 300-dimension float precision; every rank past that is ordered by the shipped
64-dimension quantized vectors, where a few hundred places either way is invisible. Since the
result panel only ever shows ranks 1-100, it is always inside the exact range. A GUESS far outside
the exact range (a rank in the high thousands) is still directionally correct — far from the
secret — even though its precise numeric rank could shift a little between generator runs; nothing
in this game promises rank stability for far guesses across a data regeneration, only that a
regeneration is safe for existing saves (see "Persistence" above).

## Layout: one screen, no scrolling

`docs/BUILDING-A-GAME.md`'s no-scroll rule (root `CLAUDE.md` repeats it) applies here like
everywhere else. The guess list is the one part of this screen whose content genuinely varies in
length (a long session can have dozens of guesses), so it is fit by MEASUREMENT
(`docs/BUILDING-A-GAME.md` Part 3), not a formula: `_rebuildList()` renders the FULL sorted list of
guesses into `.ct-list`, then `_layoutList()` removes rows from the bottom (worst rank first, since
the list is sorted best-first) until `.ct-list`'s `scrollHeight` fits `.ct-listwrap`'s actual
`clientHeight`, showing a "+N more" line for whatever was trimmed. **Rebuild-then-trim, not
trim-in-place** — an earlier version of this file trimmed the live list directly, which meant a
later viewport GROWING (e.g. rotating back to portrait, or the on-screen keyboard closing) could
never bring a previously-trimmed row back, since it was already gone from the DOM. `_rebuildList()`
is what both the initial render and `onViewportResize`'s callback call, for exactly that reason.

The result panel's "Closest words" section is a 10-per-page PAGER over ranks 1-100 rather than a
scrollable 100-row list, for the same no-scroll reason — see `docs/BUILDING-A-GAME.md`'s note under
`css/ui.css`'s `.gh-modal` that a modal CAN scroll internally past `86vh`; this game keeps every
modal's content short enough by construction that it never has to.

## Colorblind-safe closeness bands

Every guess row carries a SHAPE as well as a hue, never color alone (root `CLAUDE.md`,
accessibility conventions) — `bandShapeSVG()` in `js/ui.js`:

| Band | Rank | Color | Shape |
|---|---|---|---|
| close | `<= CLOSE` (300) | blue (`--ct-close-bar`) | diamond |
| near | `<= NEAR` (1000) | yellow (`--ct-near-bar`) | circle |
| far | everything else | gray (`--ct-far-bar`) | square |

The same shapes appear in the how-to-play diagram, so the legend a player learns on the guess list
is the same one the tutorial teaches — nothing bespoke to either screen.

## The keyboard stays up between guesses (2026-09-28)

Matt: *"When I guess a word, the keyboard minimizes... allow me to immediately begin typing my next
guess."* Two causes, both fixed in `ui.js`:

- **A guess or a hint must NOT call `renderPlay()`.** That rebuilds the whole screen, which destroys
  the text field, and a phone closes its keyboard when the focused field disappears. They call
  `_refreshPlay()`, which updates the counters, message, latest row and list in place and keeps the
  same `<input>`. Only a genuinely new screen (language switch, loading, a different puzzle) does a
  full render.
- **The Go button cancels `pointerdown`**, so tapping it never moves focus off the field (the click
  still submits). Enter was already fine once the field survived.

Verified in Chromium with touch emulation: the same input element is still `document.activeElement`
after Enter, after tapping Go, after an unknown word and after a hint. Not yet confirmed on a real
iPhone.

## Band colors: blue / yellow / gray, solid (2026-09-28)

Matt: *"please make the colors easier for me to see during the game."* The bars were teal / yellow /
vermilion at 13% strength (`#RRGGBB22`), nearly invisible, and yellow vs vermilion is the pair red/
green colorblind eyes confuse. He picked option "1" of a mockup: SOLID bars, **blue close, yellow
medium, gray far**, each with a dark (light-mode) or light (dark-mode) shape marker still on it.
Blue vs yellow is the contrast that survives red/green colorblindness; gray differs from both in
lightness. The colors are CSS variables in `contexto.css` (`--ct-<band>-bar` / `--ct-<band>-mark`,
light and `.gh-dark` sets); `ui.js` only names the band, so the rows, the shape markers and the
how-to diagram all follow the theme.

## Leaderboard: MEDALS (2026-09-29; replaces the 2026-09-28 "no-hint solves only" board)

Matt: *"gold being no hints, silver being 1 and bronze being 2, then more than 2 hints is a win, but
not an award. And the leaderboard should show the number of their most impressive score ... Tie
breaker ... should go to the person whose average number of guesses is lower."*

- **The rule lives once**: `contextoMedal(hints)` in `js/game-stats.js` (0 gold, 1 silver, 2 bronze,
  3+ null). The recorder counts gold as `ct.noHint` (it predates medals) and `ct.silver` /
  `ct.bronze`; a solve with no medal is `solved - noHint - silver - bronze`. The result panel shows
  the medal won; How to Play has a one-line legend.
- **Board order** (`js/leaderboard-rank.js`, pure and tested): golds, then silvers, then bronzes,
  then plain solves (`ctMedalScore` packs them into one number so the ordinary board machinery
  works), then the LOWER average guesses (`compareContexto`, wired in `boardMetricCmp`). Equal on
  both = tied badge. The row's big number is the player's BEST medal and how many of it
  (`ctBest`, e.g. "🥇 2 gold"); the subline lists every medal and the average guesses so the
  order can be read off the rows. The medal emoji carry 1/2/3 in their faces, so no colour is needed.
- **Solves recorded before medals were carried forward, not guessed** (rule 3/4):
  `backfillContextoMedals` runs ONCE per store (`ct.medalsV`) from `ui.js` init, counting 1- and
  2-hint wins in this device's own save, CAPPED at the hint solves the store actually recorded (the
  save is per device, the store per player). Until a device opens Contexto on the new build, its
  old hint solves rank as plain solves.
- Contexto is in `players-agg.js`'s `SOLO` set, so its solves never count toward cross-game wins.

## Every guess is reachable, and the screen is sized to the LAYOUT viewport (2026-09-29)

Matt, with a screenshot of one guess and "+2 more" on a half-empty screen: *"I can't see the 2 other
guesses even after clicking on the +2. I should always be able to see all my guesses if I want to."*

- **"+N more, show all" is a button** (44px) that opens **All guesses**: every guess, best first,
  ten to a page with a pager (`openAll` / `_renderAll`). Paged, never scrolled.
- **The half-empty screen**: `_positionRoot` sized the root to `visualViewport.height`. On an
  iPhone the keyboard shrinks only the visual viewport, and `js/viewport.js` fires on WINDOW size
  changes, so a full render while the keyboard was up (the win panel) left the game sized to the
  half screen above the keyboard, and closing the keyboard never grew it back. It now sizes to
  `window.innerHeight`, which the keyboard does not change; the input is at the top, so the keyboard
  never covers it. Sudoku uses the old formula safely only because it has no text field.

## Only COMMON words are ranked (2026-10-11)

Matt: *"It seems more difficult than the real website game."* Measured on the old data: 58% of
every secret's 300 closest words were outside the 10,000 most common words ("gneiss", "tuff" and
"quartzite" for rock, "sagacity" for wisdom). Nobody guesses those, but each one pushed the words
people DO guess further down the list (ocean: fish #141, wave #252).

- **`RANKED = 15000`** in `build-contexto-data.mjs`: only the 15,000 most frequent words, plus every
  secret, have a rank of their own. The data file carries it as `ranked`. Measured after: an
  everyday guess's rank roughly halves (ocean: fish 141 -> 90; cat: animal 52 -> 23, lion 130 -> 62).
- **A rarer word is still a legal guess.** `engine.js` `rankOf()` places it among the ranked words
  by compressed closeness (2 + how many ranked words are closer), so it can share a number with a
  ranked word. Hints and "Closest words" only ever show ranked words.
- **`words`, `forms` and `secrets` were byte-identical before and after the regeneration**, so every
  puzzle number keeps its word and every save still resolves. Ranks shown for guesses in old saves
  change (they are recomputed on every render, see "Persistence"); finished results and stats do
  not.
- `model.size` is now the RANKED count (the bar widths use it); `model.words.length` is the whole
  vocabulary. A data file without `ranked` ranks every word, as before.
- **Considered and NOT done (Matt chose fix 1 only):** ranks past 1,000 come from 64-d compressed
  vectors and are often off by 1.5x, sometimes 4x (measured: p50 1.4-1.6x, p90 3.9-7.3x across the
  exact range). More exact neighbours (K 1000 -> ~3000) and/or 128-d vectors would fix it at roughly
  6-7 MB per language (estimate, not built).

## What is NOT covered by a test

`node contexto/js/test.js` covers the engine (the word model, the ranking, the puzzle-number
maths, `hintRank`) headlessly, against the real generated data files. Nothing here has a headless
test for `js/ui.js` itself — same gap most of this repo's non-immersive puzzle games have (Sudoku's
own CLAUDE.md states the same limit) — beyond `check-no-scroll.mjs`'s two extra-screen entries (how
to play, previous games) and a manual Playwright pass (typing real guesses, a hint, give up,
previous games, reload-resume, both hosts, both phone heights, light/dark, EN/ES).
